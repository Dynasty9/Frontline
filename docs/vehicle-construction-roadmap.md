# Shared vehicle construction roadmap: 30 opportunities

Source audit against `origin/main` at `68bca12`. This is a proposed implementation roadmap, not a claim that these changes have shipped or that new renders have been visually approved.

Start with **surface-following panels, real openings, fitted glazing and door assemblies**. These affect large visible areas across vehicle families and let a single construction improvement propagate. Small equipment remains useful, but should follow the body work rather than consume the first pass.

## Scope and existing coverage

Reviewed the twelve `vm_*.gd` vehicle family builders, their helper construction, the [dispatcher](../scripts/game/vehicle_models.gd), and the shared body, cab, glazing, frame, wheel, track, rotor, cloth and fitting libraries. The audit covers core ground vehicles, NATO, CSAT, independent, civilian, helicopters, planes, attack aircraft, fighters, gunships, boats and ships. The examples below are source evidence and initial adoption targets, not a complete migration manifest.

The dispatcher resolves model aliases before trying core, gunship, attack and fighter builders. Some older `VehicleModels` and `VmPlane` implementations are therefore bypassed: notably Wipeout, Black Wasp and Blackfish copies. They are not additional consumers. Ambient `build_car` construction remains active and belongs in eventual ground-body rollout. Before each implementation, enumerate reachable model keys and variants, then migrate every matching active builder; do not rely on family key lists alone.

Existing [shared components](vehicle-components.md) already cover rectangular panels, quadrilateral glazing, tube paths, tyres, track shoes, rotor blades, cloth covers, antennas, mirrors, barrels, grilles and exhaust fittings. The last ten equipment features (lamps, cans, shackles, smoke tubes, periscopes, round hatches, tail clusters and lifting eyes) are excluded as new work. Rows below explicitly extend those foundations or extract larger construction techniques. A shared material alone does not fix a flat silhouette, missing opening or poorly attached assembly.

## Priorities and confirmed reuse

Rank reflects visible area, reuse across distinct designs/families, enabling value and implementation risk. It is a qualitative ranking, not measured performance or a time estimate. **S/M/L** means localized helper / assembly with several adapters / topology or animation-sensitive migration. The first linked vehicle is the pilot; the next two are minimum rollout checks. Variants of one vehicle do not satisfy the three-design requirement. Dependency numbers describe implementation order, so a lower-ranked kernel can be extracted just in time for a higher-ranked result.

## How to build the high-value body pipeline

Keep silhouette data in family builders. A surface adapter should expose a local two-dimensional domain, position and outward normal; planar faces, helicopter hulls and aircraft station lofts can implement it differently. `VmHeli.Hull.patch`, `VmPlane` station sampling and fighter projection are useful donors. Extract only the shared operations needed by the pilot; row 23 must not become a prerequisite rewrite of every hull.

A panel declaration supplies a boundary and edge treatment. It produces skin thickness and returns attachment frames, which row 5 uses for seams and fasteners. Row 2 changes the underlying shell topology and produces reveals. Row 3 consumes the resulting opening boundary. Row 4 assembles the door leaf, hardware anchors and optional window. This division prevents four unrelated copies of the same outline and keeps the proposed features independently useful. Row 13 supplies reusable hardware meshes to doors, cargo gates and storage bins; it does not duplicate door construction.

Use local material coordinates in metres so paint relief, cloth weave and rubber texture scale stay consistent across differently sized panels. Keep metal folded edges, rubber seals, plastic mouldings and cloth hems as distinct treatments. Existing `VehicleMaterials` and `VehicleCloth` remain the starting point; new texture acquisition is not a prerequisite for this roadmap. Evaluate any missing finish only after geometry, normals and material scale are correct.

**First implementation slice:** pilot fitted panels and door boundaries on Hunter; prove the surface adapter on Ghost Hawk and AC-130 before freezing the API. Then introduce actual openings and glazing on one enclosed cab, one helicopter and one marine cabin. Do not enable clear glass over a solid hull. Complete each technique's matching active consumers before starting the next technique; foundations may be extracted alongside their first visible consumer.

**Subsequent slices:** rows 5–8 improve the broad exterior; rows 9–20 cover running gear, access, interiors and carried equipment; rows 21–29 consolidate aircraft construction; row 30 closes the marine fitting gap. Dependencies take precedence over this grouping. Rank 23 can begin with a small profile adapter needed by row 22, without replacing all existing hull meshes.

## Completion and review gates for each technique

1. Record the reachable model keys, active builder and all matching call sites. Start with the three distinct designs named above; apply to the remaining compatible designs and list genuine exceptions. Shared construction should preserve unique silhouettes, dimensions and layouts.
2. Capture a baseline before editing. Compare identical camera, light, material, team and distance on each migrated design, with both a feature close-up and a normal gameplay view. A refactor alone does not satisfy the visual improvement goal; identify the visible improvement or classify it honestly as enabling work.
3. Check mirrored sides and compound rotations, outward normals, seams, thickness, intersections and wheel/weapon clearances. For openings, verify the reveal, interior and far opaque fallback together. Keep wreck materials and visibility behavior intact.
4. Preserve animation parents, wheel registration, weapon sockets, rotor `Blades`/`Blur`, and `Gear`/`GearUp` contracts. Aircraft propellers sometimes use `k.wheels`; static landing wheels must not accidentally join that animation list.
5. Measure meshes, surfaces/materials, vertices, draw calls and build time against the baseline before setting a per-feature budget. Keep opaque parts in the existing merge/LOD path; do not leave one node per bolt or add material variants for every part. Retain optimized ship rail construction where a generic implementation costs more.
6. Run relevant component/material/LOD/motion tests, then smoke-test all reachable vehicles and inspect the changed designs in Compatibility and Forward+ rendering. Test cache keys with different shapes, mirrored sides and repeated builds; do not reuse a cached mesh merely because the vehicle names match.
7. Keep raw screenshots outside Git. Publish one compact labeled before/after contact sheet per implementation PR, or a short video when motion is the change. Show all changed designs in the combined review evidence; split PR scope if the sheet becomes unreadable. No screenshots are needed for this planning-only PR.

The first deliverable should demonstrate a reusable construction improvement on visibly different bodies, not thirty new helper names. Each later PR should state which technique shipped, which active designs adopted it, what visibly improved, and what remains deliberately vehicle-specific.
